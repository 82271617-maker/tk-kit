# TK 剪辑业务流 · AI 化改造评估

> 评估对象：飞书《TK剪辑全流程》<https://my.feishu.cn/wiki/OA4QwZl3oi9bZ6kBapvcOqQlnmb>（3 大流程 / 8 个动作节点）
> 问题：哪些节点能交给 AI？做成 skill 还是别的形式？怎么让团队也能用？
> 日期：2026-10-31

---

## 0. 一句话结论

**AI 能替掉大约 70–80% 的"手"，替不掉 20% 的"眼"。**

- 能替的：下载、转写、翻译、改写、配音、去气口、对轴、套模板、初筛合规——这些都是**有明确输入输出的确定性动作**。
- 替不掉的：**选哪条片子值得改**、**文案好不好笑/好不好看**、**成片发不发**。这三件是判断题，不是执行题。

形式上也别只押一个：**skill 负责"让 AI 知道怎么做、做成什么样"，脚本负责"机器稳定地做"，飞书机器人负责"团队随手就能用"**。三者是叠起来的，不是三选一。

## 1. 逐个节点：能不能替、用什么替

图例：**A = 可完全替代**（人只验收）· **B = 半替代**（AI 出初稿，人定稿）· **C = 保留人工**

### 流程一 · 找素材

| # | 节点 | 判定 | 用什么做 | 说明 / 风险 |
| --- | --- | --- | --- | --- |
| 1 | 登录 TK 网页版 | C | 人 | 纯登录动作，AI 替代无收益；可存 cookie 复用 |
| 2 | 关注同类型账号 / 对标账号表 | B | 工作流 + 表格 | 账号初筛、打分、写进多维表格可自动；抓取受平台风控限制，别硬爬 |
| 3 | 找高观看率视频、复制链接 | **B** | skill（打分）+ 脚本（抓取） | 让 AI 按「观看率 / 赛道匹配 / 结构可复制 / 敏感词」打分排序，人只做最终挑一条 |
| 4 | 哼哼猫 / Snaptik 下载 | **A** | 脚本 | `yt-dlp` 原生支持 TikTok，不需要第三方站，也不怕站挂 |
| 5 | 开拍去字幕水印 | **A** | 脚本（ffmpeg） | 裁切 / delogo / 模糊三选一，比开拍可控，还免费 |

### 流程二 · 处理素材（这一段是 AI 的主战场）

| # | 节点 | 判定 | 用什么做 | 说明 / 风险 |
| --- | --- | --- | --- | --- |
| 6a | 自动生成字幕 | **A** | 脚本（whisper / faster-whisper） | 本地跑，免费、多语言、不依赖剪映 VIP |
| 6b | 字幕翻译成中文 | **A** | LLM | 一次调用，还能同时输出"逐句时间戳" |
| 6c | 导出字幕 txt | **A** | 删掉这一步 | 数据直接进流水线，不需要文件当载体 |
| 6d | GPT 改写文案（防重复 + 开头钩子） | **B** | skill（提示词 + 自评分） | 现在是"人贴提示词"，应升级为「一次出 3 版 + 自评重复度/钩子强度 + 推荐一版」 |
| 6e | 人工调整文案 | C→B | 人（审 1 版即可） | 从"改全文"降级为"三选一 + 局部改"，10 分钟内 |
| 6f | 中文译日语（口播稿） | **A** | LLM + 硬约束 | 约束：口语化、每句字数 ≤ 配音时长、不用书面语 |
| 7a | 克隆声音 | **B** | TTS API | ⚠️ 用他人声音样本克隆有法律风险，日本市场尤其敏感。建议换**有商业授权的音色** |
| 7b | 生成日语配音并下载 | **A** | 脚本 | 逐句生成，直接拿到每句时长 |
| 7c | 去气口（pc404 / DSH） | **A** | 脚本（ffmpeg silenceremove） | 也可靠"逐句 TTS"从源头消灭气口 |
| 7d | 字幕音频对轴（JingleBox） | **A** | 删掉这一步 | **关键优化**：整段 TTS 才需要对轴；逐句 TTS 天然带时间戳，这一整步可以消失 |
| 7e | 上传剪映 | B | 脚本（生成草稿） | 剪映无公开 API，但可以生成 draft 工程文件，双击即开工 |

### 流程三 · 剪辑

| # | 节点 | 判定 | 用什么做 | 说明 / 风险 |
| --- | --- | --- | --- | --- |
| 8a | 剪画面、卡点 | **B** | 脚本 + 模板 | 按字幕时间轴切、按句子卡点可自动；创意转场留给人 |
| 8b | 换字体（不用系统字） | **A** | 模板 | 固化成一套模板，不靠自觉 |
| 8c | BGM 加速 | **A** | 脚本 | ffmpeg `atempo`，统一 1.1–1.2x |
| 8d | 贴纸 / 滤镜 | **B** | 模板 | 做 3 套固定样式，按题材选 |
| 8e | 去水印 | **A** | 脚本 | 同第 5 步，同一套工具函数 |
| 8f | 红线（血腥 / 水印 / 字体 / 违规） | **B** | skill 初筛 + 人终审 | AI 过一遍画面和文案，出"红黄绿"结论；发布决定永远留给人 |

**统计**：18 个动作里，A 类 12 个、B 类 5 个、C 类 1 个。也就是说，**能全自动的占三分之二，剩下的全是"判断"**。这也决定了组织形式——自动化的部分必须是脚本，判断的部分才需要 skill 和 agent。

## 2. skill 还是什么形式：四层结构

先纠正一个常见误解：

> **skill 不是自动化。** skill 是写给 AI（和人）看的「怎么做、做成什么样、什么算合格」；它不会替你下载视频、不会替你调 TTS。
> **脚本才是自动化。** 它不稳定理解、不解释、不接受模糊需求，但快、便宜、可重复。

所以正确的组合是四层：

| 层 | 形式 | 解决什么 | 对应节点 | 团队怎么共享 |
| --- | --- | --- | --- | --- |
| L1 真相层 | 飞书知识库 + 模板文件 | 标准只有一个版本 | 全流程 SOP、提示词、检查表 | 云文档，已有 |
| L2 能力层 | **skill（SKILL.md + references + assets）** | AI 知道按什么标准做、怎么自检 | 选题打分、文案改写、合规初筛 | git repo，成员装到 `~/.dsh/skills/` |
| L3 执行层 | **脚本（python / ffmpeg / yt-dlp / TTS API）** | 确定性动作稳定跑 | 4、5、6a、7b、7c、8c、8e | 同一个 repo，`make` 一条命令 |
| L4 入口层 | **飞书机器人 / n8n** | 团队不用装环境，@ 一下就行 | 批量跑、定时跑、审核队列 | 群机器人 + 多维表格状态 |

一句话选型：

- **要 AI 做判断 → skill**（选题、改写、合规、审片建议）
- **要机器反复做同一件事 → 脚本**（下载、转写、TTS、去气口、去水印）
- **要团队零门槛用 → 飞书机器人**（入口，不是能力）
- **要人看得见进度 → 多维表格**（状态机：待选 / 待改 / 待审 / 已发）

### 不建议的做法

| 做法 | 为什么不建议 |
| --- | --- |
| 一步一个 skill（8 个 skill） | 碎、互相不知道彼此、维护成本高。skill 应对齐**交付物**，不是步骤 |
| 把确定性动作也写成 skill | AI 每次重新"理解"一遍下载命令，又慢又贵，还会编 |
| 只做飞书机器人不做脚本 | 机器人里还是人肉操作，只是换了个聊天窗口 |
| 让 AI 直接发布 | 版权、违规、声音授权，出事是账号级的 |

## 3. 团队可用的落地形态（具体一点）

```
tk-kit/                          ← git 仓库，一个人维护，团队 clone
├── skills/
│   ├── tk-select/               ← 选题打分：候选链接 → 打分表 + 推荐
│   │   ├── SKILL.md
│   │   └── references/scoring.md
│   ├── tk-rewrite/              ← 改写 + 日语口播稿 + 自评
│   │   ├── SKILL.md
│   │   ├── references/prompts/  ← 现在飞书里的两个 txt 提示词
│   │   └── assets/checklist.md
│   └── tk-review/               ← 发布前 6 项 + 红线初筛
├── scripts/
│   ├── fetch.sh                 ← yt-dlp 下载
│   ├── transcribe.py            ← whisper 出字幕 + 时间戳
│   ├── tts.py                   ← 逐句配音 + 时间戳
│   ├── clean.py                 ← 去水印 / 去气口 / BGM 加速
│   └── make/SKILL.md            ← 一条命令串起来
├── prompts/                     ← 提示词版本化，改一次全团队生效
└── README.md                    ← 装法 + 三个典型命令
```

安装（每人一次）：

```bash
git clone <repo> ~/tk-kit && ln -s ~/tk-kit/skills/* ~/.dsh/skills/
```

三个入口给三种人：

| 角色 | 用什么 | 日常 |
| --- | --- | --- |
| 你自己 | DSH + `make` | 一条命令出素材包，审片后发 |
| 剪辑同事 | 飞书机器人 | 丢链接进群，机器人回"脚本 + 配音 + 草稿包" |
| 运营/老板 | 多维表格 | 看队列和通过率，不碰工具 |

## 4. 分期建设（按 ROI 排，不按节点排）

### P0 · 文案流水线（1 周，纯文本，零第三方依赖）
把 6a–6f 串成一条：字幕 → 中文 → 改写 3 版 → 日语口播稿 → 自评。
**收益**：现在最费时的"贴提示词 + 改文案 + 再翻译"从 40 分钟压到 5 分钟；且不依赖任何会挂的网站。
**验收**：同一条原片，3 个不同的人跑出来，脚本质量差异 < 10%。

### P1 · 素材流水线（2–3 周）
`yt-dlp` 下载 + ffmpeg 去水印 + 逐句 TTS + 去气口，替掉哼哼猫 / 开拍 / pc404 / JingleBox 四个外部站点。
**顺带收益**：删掉"对轴"和"导出 txt"两个节点。

### P2 · 剪映草稿（1 个月，可选）
生成 draft 工程文件，剪辑同事"双击即开工"，素材、字幕、字体、BGM 都已就位。
**风险**：草稿格式非官方，剪映升级会坏，要留降级方案（导出素材包）。

### P3 · 团队化（1 个月）
飞书机器人 + 多维表格状态机 + 权限/成本控制。

## 5. 风险，必须写在方案里

| 风险 | 具体表现 | 应对 |
| --- | --- | --- |
| **声音授权** | 克隆他人（含声优）声音，日本市场法律风险高 | 只用有商业授权的音色；样本来源留痕 |
| **平台判定搬运** | AI 提高产量 → 重复度也提高 → 批量限流 | 把"改写深度"做成硬指标（句式/例子/顺序三项都要变），宁慢勿滥 |
| **第三方站不稳定** | 哼哼猫 / 开拍 / pc404 / JingleBox 随时改版或收费 | 优先自建（yt-dlp + ffmpeg + whisper），第三方只做备选 |
| **剪映草稿格式** | 非公开 API，版本升级即失效 | 草稿只是加速器，主线交付物是素材包 |
| **内容合规** | 血腥、水印、新闻版权 | AI 初筛 + 人终审，发布按钮永远在人手里 |
| **成本失控** | TTS 按字计费，批量跑会烧钱 | 单条成本上限 + 每日配额 + 失败不重试 |
